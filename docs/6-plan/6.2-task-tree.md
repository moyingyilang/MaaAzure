# 6.2 · 任务树与分批

**位置**：`6-plan` › 6.2 ｜ 前置：[6.1 路线图](6.1-roadmap.md) ｜ 后继：[6.3 风险](6.3-risks.md)

93 个任务不按字母排，按**实现形状**分四类。分错类会让 P1 阶段返工。

## 分类树

```
A 类 · 纯点击序列（约 35 个）
├── 只有「看见就点」，无跨帧记忆
├── 实现：只有 JSON，0 行 Rust
└── 例：dorm_fill, tactical, private_quarters 互动, reward 领取

B 类 · 点击 + 判读（约 25 个）
├── 需要读一个数/一段文字再决定点不点
├── 实现：JSON + 1 个 Custom（决策函数 <30 行）
└── 例：commission 选最短, research 立项, shop 购买, exercise 选对手

C 类 · 需要寻路 / 阈值（约 20 个）
├── 有地图模型或状态累积
├── 实现：JSON 外壳 + Rust 状态机
└── 例：campaign 推图, combat 撤退, os 进图, sos, war_archives

D 类 · 大型状态机（约 13 个）
├── 多个子系统互相依赖，单个模块 >2,000 行
├── 实现：独立子模块 + 自己的测试集
└── 例：os_hazard1_leveling, os_explore, island_*, gems_farming
```

## 为什么先做 A 类

1. **最快验证 Pipeline 规范是否够用**：A 类写不出来，说明规范错了，早发现比晚发现便宜。
2. **A 类的拓扑是 B/C 类的地基**：主界面、弹窗、返回、翻页这些节点，A 类会先做完。
3. **A 类能最快产出可用的东西**：P1 结束就是一个「比旧版更省」的日常脚本。

## A 类的验收信号

如果 35 个 A 类任务里有 **≥3 个被迫写 Custom**，说明：
- 要么它们被误分类（其实是 B 类）——修正分类；
- 要么 Pipeline 规范缺了某条约定（比如翻页）——修订 [3.1](../3-authoring/3.1-pipeline-spec.md)。

这两种情况都要在 P1 结束前解决，不能带着进 P2。

## 每个任务的交付定义

```
一个任务算「迁完」，需要同时满足：
├── resource/pipeline/<层>/<domain>/ 下有 entry.json + nodes.json
├── 通过 pipeline-check（引用/孤图/可达性）
├── 有至少 1 个 golden 用例且 L1+L2 通过
├── 在真实模拟器上连跑 5 次成功
└── 在 docs/parity.md 打勾（P4 建表）
```

**只有 JSON 没有用例的任务不算迁完。** 否则 P2 改共享节点时会静默破坏 P1 的任务。

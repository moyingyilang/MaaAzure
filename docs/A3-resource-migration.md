# A3 · 资源与数据迁移

新线**一个 Python 文件都不跑**，但旧仓有三种「资产」必须搬过来，而且**都不是手写重做**：

| 资产 | 规模 | 形态 | 迁移方式 |
|---|---|---|---|
| 模板图 | 7,786 张 / 152 MB | PNG，按 server/module 分目录 | 路径规范化 + 复制 |
| 资源定义 | 61 个 `assets.py`（**100% 自动生成**） | `Button(...)` / `Template(...)` 定长表达式 | AST 解析 → 生成 Pipeline 节点 |
| 战役地图 | 1,436 个 `.py` | `CampaignMap` 属性赋值 + 文本网格 | AST 提取字面量 → JSON |
| 配置项 | 2,401 项 | `args.json`（由 4 层 YAML 生成） | → `interface.json`（PI v2） |
| 多语言 | 5 种 × N 键 | `i18n/*.json` | → PI `languages` 分片 |

关键发现：**`module/**/assets.py` 全部 61 个文件都带
`# This file was automatically generated by dev_tools/button_extract.py` 头**
（`61/61`），也就是说资源定义是**机器生成的定长表达式**，共 1,781 个 `Button` + 601 个 `Template`。
这让资源层迁移从「人工重做」变成「写一个转换器」，是整个计划里性价比最高的一块。

---

## 1. 模板图：`assets/` → `resource/image/`

### 现状

```
assets/
├── cn/            # 4 个服务器各一份：cn / en / jp / tw
│   ├── commission/COMMISSION_ADVICE.png
│   ├── map/...
│   └── ...
└── ...
```

`Button.file` 是 `{'cn': './assets/cn/commission/COMMISSION_ADVICE.png', ...}` 形式的
**分服务器路径映射**，运行时由 `server.server` 全局变量选一份。

### 目标

```
resource/image/
├── cn/commission/commission_advice.png
├── en/commission/commission_advice.png
└── ...
```

规则：

1. **保留 server 一级目录**，因为 MaaFramework 的 bundle 是「后加载覆盖同路径」，
   多服务器靠加载不同的 bundle 路径实现（`resource.path: ["./resource", "./resource/cn"]`），
   不需要在资源里做变量替换——这一点比旧版更干净。
2. **文件名小写下划线**，与节点名一致（A2 §3），让 `xtask` 能从图片反推节点。
3. **不改像素**。1280×720 的裁图原样保留，靠 Controller 的 `display_short_side: 720`
   做归一化（DEC-007，P0 需实测阈值漂移）。
4. GIF 模板（`Template` 支持动图）：MaaFW **不支持** GIF 模板匹配。
   需先统计有多少个，逐个决定「取首帧」还是「改用 `And` 组合多帧特征」。

转换器：`xtask convert-images`
- 输入 `../AzurPilot/assets`，输出 `resource/image`
- 输出 `image_index.json`（旧路径 ↔ 新路径 ↔ 所属模块），供后续步骤引用
- 幂等：以 `image_index.json` 为准，重复运行不产生差异

**待统计项**：`.gif` 模板数量（`find assets -name '*.gif' | wc -l`），P0 第一件事。

## 2. 资源定义：`Button` / `Template` → Pipeline 节点

### 为什么能自动生成

`button_extract.py` 输出的表达式是定长的：

```python
COMMISSION_ADVICE = Button(
    area={'cn': (871, 322, 999, 383), 'en': ..., 'jp': ..., 'tw': ...},
    color={'cn': (230, 177, 116), ...},
    button={'cn': (871, 322, 999, 383), ...},
    file={'cn': './assets/cn/commission/COMMISSION_ADVICE.png', ...},
)
```

`area` = 检测区域，`color` = 期望平均色，`button` = 点击区域，`file` = 模板图。
这四个字段**恰好一一对应** MaaFW 的节点字段：

| 旧字段 | 新字段 | 说明 |
|---|---|---|
| `file` | `template` | 模板图路径（去掉 `./assets/<server>/` 前缀） |
| `area` | `roi` | 检测区域（可选，给了更稳更快） |
| `button` | `target` | 点击区域；`Click` 动作的落点 |
| `color` | `ColorMatch.expected` | 平均色匹配 |
| `Button` 有 `file` | `recognition: TemplateMatch` | 有模板图优先模板匹配 |
| `Button` 无 `file` | `recognition: ColorMatch` | 只有颜色的纯色检测 |
| `Template` | `recognition: TemplateMatch`（无 `roi`） | 全屏模板 |

### 生成结果

```jsonc
// 自动生成：resource/pipeline/gen/commission.json
{
  "commission_advice": {
    "recognition": "TemplateMatch",
    "template": "cn/commission/commission_advice.png",
    "roi": [871, 322, 999, 383],
    "action": "Click",
    "target": [871, 322, 999, 383],
    "next": []                                  // ← 留给人工补
  },
  "commission_has_pending": {
    "recognition": "ColorMatch",                 // 无 file 的纯色按钮
    "roi": [320, 288, 380, 338],
    "expected": [121, 113, 152],
    "action": "DoNothing",
    "next": []
  }
}
```

**自动生成的部分是「叶子」，`next` 是空的。** 拓扑（谁接谁）必须人工写，
这正是我们要保留的领域知识，也是 Pipeline 不可自动生成的部分。

### 工作量估算

- 1,781 Button + 601 Template = 2,382 个节点骨架：`xtask` 全自动
- 这 2,382 个节点里有真实用途的估计 40–50%（其余是别名、调试用、跨服务器重复）
- 人工只需要：给 20 个日常任务的入口写 `next` 拓扑。按 A2 示例的粒度，
  一个任务 30–60 个节点，**每任务 1–2 天**
- 生成文件放 `pipeline/gen/`，**不手改**；人工拓扑放 `pipeline/<module>/`，
  CI 检查 `gen/` 的 diff 必须来自 `xtask` 重跑

### 名字映射

节点名 = 旧常量名小写：`COMMISSION_ADVICE` → `commission_advice`。
冲突处理：跨模块同名（如多个 `OCR_FUEL_MAXED`）加模块前缀 `commission_ocr_fuel_maxed`。
`xtask` 检测冲突并列出，人工确认后写入 `merge_rename.json`。

## 3. 战役地图：`campaign/*.py` → `data/campaign/*.json`

### 现状

1,436 个文件，形态高度规律：

```python
MAP = CampaignMap('12-4')
MAP.shape = 'K8'
MAP.camera_data = ['D2', 'D6', 'H2', 'H6']
MAP.map_data = """
    MB MB ME -- ME ++ ++ ++ MB MB ++
    ...
"""
MAP.weight_data = """
    50 50 ...
"""
MAP.spawn_data = [
    {'battle': 0, 'enemy': 2},
    ...
]
```

### 目标

```jsonc
// data/campaign/12-4.json
{
  "chapter": "12-4",
  "shape": "K8",
  "camera_data": ["D2", "D6", "H2", "H6"],
  "camera_data_spawn_point": ["D6"],
  "map_data": ["MB MB ME -- ...", "..."],       // 解析后按行存
  "weight_data": [[50, 50, ...], ...],
  "spawn_data": [{"battle": 0, "enemy": 2}, ...],
  "flags": { "road_blocks": true },              // 记录 MAP.road_blocks() 之类调用
  "source": "campaign/campaign_hard/campaign_12_4.py"
}
```

### 提取策略

用 `ast` 遍历，**只接受字面量**，遇到无法静态求值的表达式就报错并列出待人工处理清单：

| 情况 | 处理 |
|---|---|
| `str` / `int` / `float` / `list` / `dict` / `tuple` / 三引号文本 | `ast.literal_eval` 直接取 |
| `MAP.xxx = <字面量>` | 记录字段 |
| `MAP.road_blocks()` / `MAP.camera_sight = (...)` 等调用 | 记录到 `flags` |
| `from campaign.campaign_main.campaign_12_1 import Config` | 记录继承来源，转换后合并到当前 JSON |
| 三引号网格 | 按行 split + 按空格 split，校验行宽一致 |

**校验器**（必须做）：
- 网格行列数必须等于 `shape`（`K`=11 列，`8`=8 行）
- 每行 token 必须在合法符号集 `{++, --, SP, ME, MB, MM, MA, MS, __, Me, ...}`
- `spawn_data` 长度与 `battle` 递增一致
- 转换后再用 Rust 侧 `maazure-battle` 读一遍，与旧版 Python 读取的结果做**逐字段 diff**

### 部署

- `data/campaign/` 随二进制发布，不打进 `resource/`（它不是 MaaFW 资源）
- `maazure-battle` 里用 `include_dir!` 或运行时读文件；优先运行时读，
  因为 1,436 个文件编译进二进制会让增量编译变慢
- 活动战役目录（`campaign_event/`）按目录结构保留，才能「删旧活动 = 删目录」

## 4. 配置：2,401 项 → `interface.json`（PI v2）

### 现状

旧版用 4 层 YAML 管道（`task.yaml` + `argument.yaml` + `override.yaml` + `default.yaml`）
生成 `args.json`，再由 GUI 渲染 2,401 个配置项，运行时以 `Main.Campaign.Name` 点分路径访问。

### 目标

PI v2 的 `option` 系统直接接过这一层：

| 旧概念 | PI v2 |
|---|---|
| `argument` 定义（type/value/option/validate） | `option` + `case`（`select` / `checkbox` / `input` / `switch`） |
| `task.yaml` 的 任务→组 映射 | `task` + `group` |
| 点分路径 `Main.Campaign.Name` | `option.name` + `pipeline_override` |
| `default.yaml` / `override.yaml` | `preset` + `option.default_case` |
| 5 语言 `i18n/*.json` | `languages` + `interface_<lang>.json` |
| GUI 上的 `display: hide` | 不声明该 option 即可 |

映射器 `xtask convert-config`：
1. 读 `args.json` → 为每个 `(Task, Group, Argument)` 生成一个 `option`
2. `option` 里挂 `pipeline_override`：把用户取值注入对应 Pipeline 节点的 `expected`/`roi`/`threshold`
3. `Task` 列表 → `task[]`，`Scheduler.Command` 之类内部字段丢弃
4. 生成 `interface.json` 骨架（人工补 `label`/`description`/`icon`）

**不做**：把 2,401 项全量暴露给用户。默认只保留每个任务 3–8 个真正会被改的项。
其余用 `preset` 固定成合理默认，等有人提需求再放出来。
这一条能直接把 GUI 复杂度砍掉一个数量级，也是 P1 的验收内容之一。

## 5. 多语言

```jsonc
// interface.json
{ "languages": { "zh_cn": "interface_zh_cn.json", "en_us": "interface_en_us.json",
                 "ja_jp": "interface_ja_jp.json", "zh_tw": "interface_zh_tw.json" } }
```

- 从旧 `i18n/*.json` 按 key 直取，键名改成 `task.name` / `option.name` 的路径形式
- `zh-TW` 旧版是自动简繁转换的结果，迁移时**保留已有译文**，只补新增键
- 缺失译文回退顺序沿用旧版约定：`en → cn → jp → tw`
- CI 检查：`interface_*.json` 的键集合必须与 `interface.json` 中出现的 `$key` 完全一致

## 6. 迁移顺序（按依赖，不按模块大小）

| 步 | 动作 | 依赖 | 产物 |
|---|---|---|---|
| 1 | `convert-images` | 无 | `resource/image/` + `image_index.json` |
| 2 | 统计 GIF 模板数量并定处理策略 | 1 | 决策记录追加到 A8 |
| 3 | `convert-assets` 生成 2,382 个节点骨架 | 1 | `resource/pipeline/gen/*.json` |
| 4 | `convert-campaign` | 无 | `data/campaign/*.json` + 校验报告 |
| 5 | `convert-config` | 3 | `interface.json` 骨架 + i18n 分片 |
| 6 | 手工写 `00_common.json`（主界面/弹窗/恢复） | 3 | 所有任务的公共底座 |
| 7 | 逐任务写拓扑（委托 → 宿舍 → 科研 → …） | 6 | 每任务一个文件 |

**注意步骤 6 的次序**：`global_home` / `global_recover` / `popup_close` 是所有任务的地基。
地基没稳就写业务拓扑，后面每个任务都要返工。

## 7. 数据血缘（可追溯）

每个生成物都带来源：

```jsonc
// resource/pipeline/gen/commission.json 顶部
{
  "_meta": {
    "generated_by": "xtask convert-assets",
    "source": "../AzurPilot/module/commission/assets.py",
    "source_rev": "86a9463d4",
    "do_not_edit": true
  },
  "commission_advice": { ... }
}
```

`source_rev` 记录旧仓的 commit，出问题时能一眼定位「这张图是从哪一版来的」。
升级上游资源时，`xtask` 对比 `source_rev` 只重生成变化的部分。

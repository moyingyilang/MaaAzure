# 3.1 · Pipeline 规范

**位置**：`3-authoring` › 3.1 ｜ 前置：[1.2 边界](../1-foundation/1.2-boundaries.md) ｜ 后继：[3.2 节点树](3.2-node-tree.md)

> 字段细节以 [MaaFramework 流水线协议 v5.8](https://github.com/MaaXYZ/MaaFramework/blob/main/docs/zh_cn/3.1-任务流水线协议.md) 为准。
> 本文只规定**我们怎么用它**。

## 1. 为什么 Pipeline 能替掉 2,220 行寻路

| 旧概念 | Pipeline 对应 |
|---|---|
| `Page(check_button, links)` | 节点 + `next` 列表 |
| `ui_goto(page)` A* 最短路径 | 运行时逐个尝试 `next` |
| `appear_then_click(BTN, interval=2)` | `rate_limit: 2000` |
| `ui_additional()` 弹窗兜底 | `next` 末尾挂 `[JumpBack]global_popup_close` |
| 循环退出 `appear(END)` | `next` 指向结束节点 |
| `skip_first_screenshot` | `pre_wait_freezes`（等画面不动） |

已知够用的能力（v5.8）：`anchor` / `[Anchor]` / `[JumpBack]` / `max_hit` / `on_error` /
`timeout: -1` / NodeAttr 条件 / `And` `Or` / `Scroll` / `Screencap` / `Shell` / `Command`。

## 2. 文件树

```
resource/
├── common/pipeline/          ← 手写拓扑（服务器无关，写一次）
├── <server>/pipeline/gen/    ← xtask 生成的叶子（每服务器一份）
└── <server>/image/           ← 该服务器的模板图

resource/common/pipeline/
├── 0-common/                 所有任务的地基（先写这个）
│   ├── home.json             global_home + anchor
│   ├── popup.json            global_popup_close
│   └── recover.json          global_recover
├── 1-daily/                  日常任务，一个任务一个子目录
│   ├── commission/
│   │   ├── nodes.json        业务节点
│   │   └── entry.json        CommissionStart
│   └── dorm/ research/ ...
├── 2-battle/
│   ├── campaign/ combat/
└── 3-world/                  P3
```

加载顺序即覆盖顺序：`0-common` → `1-daily` → `2-battle` → `3-world`。
调试补丁放独立 bundle，靠 `default_pipeline.json` 的多 bundle 覆盖语义生效。

## 2.5 接线声明 → 生成（P1 起的写法）

手写拓扑时最烦的不是「谁接谁」，而是给每个节点抄 `template` / `roi` / `target`——抄错就静默偏移。
所以这一层拆成两件事：

| 文件 | 谁维护 | 内容 |
|---|---|---|
| `resource/wiring/<layer>/<task>.json` | **人** | 只有「谁接谁」+ 少量覆盖 |
| `resource/common/pipeline/<layer>/<task>/*.json` | `xtask build-pipeline` | 完整节点 |

```jsonc
{
  "_note": "结构草案：流程顺序未经真机验证",
  "layer": "1-daily",
  "file": "tactical/entry.json",
  "nodes": {
    "TacticalStart": { "next": ["global_home", "tactical_goto_reward"] },
    "tactical_goto_reward": {
      "use": "ui_main_goto_reward",              // 引用生成叶子，坐标不用手写
      "next": ["tactical_goto_tab", "global_recover"]
    },
    "tactical_page": {
      "use": "tactical_add_new_student",
      "action": "DoNothing",
      "next": ["tactical_start_class", "tactical_done"]
    }
  }
}
```

三条经验：

1. **页面标志与动作按钮要用不同的图**。一开始我拿 `tactical_class_start` 既当「到页面了」
   又当「开始上课」，同一个模板在同一帧同时命中两个语义，日志完全读不懂。
2. **`_note` 写在接线文件顶层**（不是 pipeline JSON）：pipeline 里任何顶层键都会被当节点，
   元信息必须待在 `wiring/` 或 `resource/manifest/`。
3. **`global_home` 的模板就是 `ui_main_goto_campaign`**，而 `ui_main_goto_*` 这一族
   （campaign / dormmenu / reshmenu …）在旧仓里**共用同一块像素**（md5 相同）。
   所以「主界面标志」与「任何一个 goto 按钮」是同一个探测器：
   它们**不能出现在同一个 `next` 列表里**，否则等于让引擎掷硬币。
   `xtask check` 会把这种写法直接报成警告（`接线歧义`），实测一开就抓到 3 处。

4. **`Start` 的 `next` 要把任务专属节点放前面、`global_home` 放后面**。
   实测 `ui_main_goto_campaign` 与 `ui_main_goto_dormmenu` 是**同一张图**
   （md5 相同，全库 57 组这样的别名），谁在前面谁先命中——`global_home` 排前面
   会让宿舍任务在主界面就「立刻完成」。

## 3. 命名

| 对象 | 规则 | 例 |
|---|---|---|
| 业务节点 | `<domain>_<state>` | `commission_page` |
| 任务入口 | `<Domain>Start` | `CommissionStart` |
| 结束 | `<domain>_done` | `commission_done` |
| 恢复 | `<domain>_recover` | `commission_recover` |
| 公共 | `global_*` | `global_home` |
| 图片 | `image/<server>/<domain>/<state>.png` | `image/cn/commission/page.png` |

**节点名 = 图片路径去扩展名、斜杠换下划线**。这条规则让 `xtask convert-assets`
能自动生成 60% 的节点骨架（[4.2](../4-migration/4.2-assets.md)）。

## 4. 全局基线

`resource/default_pipeline.json`：

```jsonc
{
  "Default": { "rate_limit": 1000, "timeout": 20000, "pre_delay": 200, "post_wait_freezes": 500 },
  "TemplateMatch": { "threshold": 0.75 },
  "OCR": { "threshold": 0.3 }
}
```

四条强制规则：

1. 每个任务的 `next` 末尾必须有 `[JumpBack]global_recover`。
2. 退出条件用「命中即结束」，**绝不**用「未命中即结束」。
3. 不在节点里做业务计数（要计数就进 Rust，见 [1.2](../1-foundation/1.2-boundaries.md)）。
4. `timeout: -1` 只允许出现在 `global_recover`。

## 5. 锚点约定

```jsonc
// 一次设置，全仓复用
"global_home": {
  "recognition": "TemplateMatch",
  "template": "common/home_flag.png",
  "anchor": "home",
  "action": "DoNothing",
  "next": []
}
```

任何任务的失败分支：`{ "next": ["[Anchor]home"] }`。

好处：回主界面不需要每题重复写路径，也没有旧版 `ui_goto_main()` 的逐页搜索。

## 6. ROI 与阈值

| 场景 | ROI | 阈值 |
|---|---|---|
| 全屏模板（大图标） | 不填 | 0.75 |
| 局部按钮 | **必填** | 0.75 |
| 小图标 / 细线 | 必填 + 放大 1.5× 的图 | 0.65 |
| 文字区域 | 必填 | 用 OCR，不用模板 |

**ROI 必填**是性能纪律：全屏模板匹配 3ms 看着不多，但 `next` 里挂 5 个就是 15ms/帧。

## 7. 校验（`pipeline-check`）

JSON 没有编译期检查，这是唯一防线。**已实现**，CI 用一条命令跑完：

```bash
cargo run -p xtask -- check      # 索引一致性 + 引用/锚点/图片/roi/孤儿 + 零 Python
```

覆盖面：

| 检查 | 失败级别 |
|---|---|
| `next` / `on_error` 引用的节点存在 | 错误 |
| `[Anchor]` 有对应的 `anchor` 设置点 | 错误 |
| `template` 指向的图片存在 | 错误 |
| 无入边且非 `*Start` 的孤儿节点 | 警告 |
| 从每个 `*Start` 出发的图可达性 | 警告 |
| 节点 `next` 长度 > 12（帧预算风险） | 警告 |
| `image_index.json` 每条引用在磁盘存在（**已实现**） | 错误 |
| `interface.d` 的 `task.entry` 在 Pipeline 里存在、option/group 引用有效（**已实现**，`config-check`） | 错误 |
| `gen/` 下的文件与 `xtask` 重跑结果一致（需要旧仓，离线校验做不到，靠 review） | 人工 |

## 8. 反模式

| 反模式 | 问题 | 正确做法 |
|---|---|---|
| 一个 `next` 挂 20 个候选 | 每帧 20 次匹配 | 按页面分组，先进页再细辨 |
| 用 `max_hit` 当循环计数 | 日志不可读、语义漂移 | Rust Custom |
| `timeout: -1` 到处用 | 卡死永不报错 | 只给 `global_recover` |
| 在 CustomAction 里 `sleep` | 阻塞 C++ 线程 | `post_wait_freezes` |
| 手改 `pipeline/gen/` | 下次生成即丢失 | 改生成器 |
| 节点名 `step1` `step2` | 日志无法定位领域 | 见 §3 |

# 5.2 · 回归测试

**位置**：`5-engineering` › 5.2 ｜ 前置：[5.1](5.1-build.md) ｜ 后继：[5.3 发布](5.3-release.md)

## 为什么这是 P0 的第一件事

旧仓 `tests/` 约 160 个测试，全部覆盖 WebUI / 进程管理 / 配置。
**游戏逻辑自动化测试数量是 0。**（旧仓文档原文：「游戏逻辑无自动化测试」）

在这个状态下重写 288k 行，等于闭眼跳崖：改错了没人知道，等用户报「大世界卡住」时，
你已经忘了两个月前改了哪一行。

**先建网，再拆楼。**

## corpus 结构

```
corpus/
├── manifest.json
└── commission/
    ├── case.json
    ├── 0001.png
    ├── 0001.decision.json
    └── ...
```

```jsonc
// 0001.decision.json
{
  "frame": 1,
  "node": "commission_page",
  "hits": { "commission_pick": true, "commission_empty": false },
```

## 录制器：已落地

`tools/corpus/record_golden.py`（约 300 行，一次性工具，跑在冻结的 AzurPilot 上）。

```bash
# 真跑录制（需要模拟器 + AzurPilot 能跑起来的环境，如 Windows）
cd ../AzurPilot
uv run python ../MaaAzure/tools/corpus/record_golden.py \
    --task commission --config alas --out ../MaaAzure/corpus

# 自检（不需要模拟器）：合成 3 帧验证产物格式
python3 ../MaaAzure/tools/corpus/record_golden.py --selftest --out corpus
```

自检通过意味着产物格式与录制链路可用；真机录制仍待 Windows 环境（本机 Termux 的
`uv run` 会卡在 psutil 编译，与录制器无关）。

| 挂载点 | 记录内容 |
|---|---|
| `device.screenshot()` | 每帧 PNG |
| `appear()` / `appear_then_click()` | 命中结果 |
| `click()` | 落点坐标 + button area |
| `Ocr` / `Digit` / `DigitCounter` | 识别文本 + 区域 |
| 任务结束 | `case.json`（任务名/服务器/结束原因） |

体积：一个日常任务 200–400 决策帧 × ~120KB ≈ **30–50MB**。20 个任务约 1GB。
**不进 git**，走 release 附件 + 本地缓存。

> 压缩用无损 WebP（可压到 1/3），**不要用 JPEG**：模板匹配对压缩伪影敏感，
> 回放结论会和新环境不一致，误判成逻辑 bug。

## 回放器：已落地

`crates/runtime/runner/src/replay.rs`：`Case::load()` 读 `case.json` + 逐帧 PNG（只读 IHDR
取宽高，不解码像素）+ `*.decision.json`；`ReplayEngine` 实现 `Engine` trait，
按顺序吐帧并记录被投递的点击/滑动，供断言比对。

```rust
pub struct ReplayEngine { frames: Vec<ImageBuf>, cursor: usize, clicks: Vec<Point> }

#[test]
fn commission_picks_shortest() {
    let case = Case::load("corpus/commission/case.json");
    let mut machine = CommissionMachine::new(cfg!());
    let mut engine = ReplayEngine::from(case);
    for expected in case.decisions() {
        let cmd = machine.step(engine.frame()).unwrap();
        assert_eq!(cmd.node(), expected.node);
        engine.apply(cmd);
    }
    assert_eq!(machine.finished(), Some(TaskOutcome::Ok));
}
```

这就是 [2.1](../2-architecture/2.1-layers.md) 要求 `domain/**` 不依赖 MaaFW 的真正原因：
**回放不需要 SDK、不需要模拟器、不需要网络。**

当前状态：回放引擎与用例加载已通过单元测试（造临时 PNG/JSON 验证帧序、决策绑定、
点击记录、空目录报错）。端到端回放要等第一台模拟器跑出真 corpus。

## 合成帧：不用模拟器跑真实 Pipeline

`maazure-daemon --synth` 用 `Controller::new_custom` 造一个「假设备」：`screencap()`
直接返回我们合成的 PNG。合成方式是把模板贴到它的 `roi` 上，于是模板匹配会命中，
Pipeline 真的往下跑。

```bash
# 让 commission_goto_reward 命中，其余不命中
maazure-daemon --synth CommissionStart --show commission_goto_reward

# 走完整条链（三个节点同时可见）
maazure-daemon --synth CommissionStart \
    --show commission_goto_reward,commission_goto_commission,commission_page
```

它验证什么、不验证什么：

| 验证 | 不验证 |
|---|---|
| 模板路径 / `roi` / 阈值自洽 | 真实画面是否长这样 |
| `next` 图与锚点跳转 | 截图时延 |
| `Custom` 节点能否被调到 | OCR 准确率 |
| FFI 全链路（Controller → Tasker → Pipeline） | 与真机的时序差异 |

实测输出（aarch64 原生，无 qemu、无模拟器）：

```
── MaaAzure synth ──
入口      CommissionStart
贴图      ["commission_goto_reward", "commission_goto_commission", "commission_page"]
── 结果 ──
耗时      2.9s
点击      [(27, 185), (565, 288)]
Pipeline  成功
```

**它抓到的三个真 bug**（都是离线检查发现不了的）：

| 现象 | 根因 | 修法 |
|---|---|---|
| `templ size is too large [image=[189,30]] [templ=[720,1280]]` | 旧仓 `Button` 资产是**整张截图**，匹配时才按 `area` 裁 | 转换器按 `area` 裁切后再落盘（[4.1](../4-migration/4.1-images.md)） |
| `get_pipeline_data failed, node not exist [name=home]` | 锚点只有被设置过才存在，任务起点写 `[Anchor]home` 必然失败 | 起点直接引用 `global_home`，锚点只用于后续节点 |
| `key already exists [key=_meta]` | MaaFW 把 pipeline JSON 的每个顶层键当节点，`_meta` 会和别的文件撞 | pipeline JSON 里禁止元信息键，元信息放 `resource/manifest/` |

### 脚本化：不依赖录像的回归用例

单帧是手工调试用的；日常回归用**脚本**（`data/fixtures/*.json`）：

```jsonc
{
  "name": "commission_happy_path",
  "entry": "CommissionStart",
  "frames": [
    { "show": ["commission_goto_reward"] },
    { "show": ["commission_goto_reward", "commission_goto_commission"] },
    { "show": ["commission_goto_reward", "commission_page"] }
  ],
  "expect": { "min_clicks": 2, "max_clicks": 6, "outcome": "ok" }
}
```

帧随点击推进，所以「点完画面变了」的流程也能覆盖。跑全部用例：

```bash
./scripts/synth-check.sh        # 在 chroot 里跑，需要带 maa feature 的二进制
```

脚本对**每个**用例做两件事：

1. `--synth --script` 跑合成帧并断言（点击次数 / 执行路径 / 结束状态）
2. `--dump` 导出成 golden corpus 布局，再 `--corpus-run` 跑一遍真实 Pipeline，
   断言「执行结果与录制一致」

第 2 步跑的是 `--corpus-run` 与真机录制**共用的同一条路径**，所以真机语料到位后，
`record_golden.py` 录出来的目录能被同一条命令消费。

当前 3 个用例，实测全过：

| 用例 | 贴图 | 期望 | 实测 |
|---|---|---|---|
| `commission_happy_path` | 三帧递进 | 2–6 次点击、ok | 2 次点击、ok |
| `global_home_only` | 只有主界面标志 | 0 次点击、ok | 0 次点击、ok |
| `nothing_matches` | 全空 | 0 次点击、**failed** | 0 次点击、failed |
| `commission_no_pick` | 只有委托页 | 0–2 次点击、ok | 0 次点击、ok |
| `tactical_start_class` | 主界面→任务→战术学院 | 3 次点击、ok | 3 次点击、ok |
| `reward_collect` | 任务→一键领取 | 2 次点击、ok | 2 次点击、ok |
| `gacha_page_only` | 进建造页即止 | 1 次点击、ok | 1 次点击、ok |
| `dorm_collect` | 宿舍→快速领取 | 3 次点击、ok | 3 次点击、ok |
| `guild_claim` | 大舰队→领报告 | 2 次点击、ok | 2 次点击、ok |
| `exercise_page_only` | 出击→演习页即止 | 2 次点击、ok | 2 次点击、ok |
| `meowfficer_page_only` | 宿舍菜单→指挥喵页即止 | 2 次点击、ok | 2 次点击、ok |
| `research_page_only` | 科研菜单→科研页即止 | 2 次点击、ok | 2 次点击、ok |
| `daily_page_only` | 出击→每日页即止 | 2 次点击、ok | 2 次点击、ok |

`nothing_matches` 是负向用例：什么都不贴时 Pipeline 必须**失败**而不是假装成功——
这条能防止「把断言写成永远通过」。

`commission_no_pick` 的入口直接设在 `commission_page`，因为从 `CommissionStart`
起必须看到「主界面→任务」按钮才走得下去；**fixture 的入口可以不是任务入口**，
只要它是图里可达的起点。

### 没有录像时也能跑「回放断言」

`--synth --dump` 会把合成帧写成 golden corpus 的布局（PNG + case.json），
于是**录制器还没跑过也能验证语料链路**：

```bash
# 1) 合成 + 跑 + 导出语料
maazure-daemon --synth --script data/fixtures/commission_happy_path.json \
    --dump corpus/synth_commission

# 2) 用这份语料喂真实 Pipeline，并和录制的结束状态对齐
maazure-daemon --corpus-run corpus/synth_commission --entry CommissionStart
```

实测输出：

```
── MaaAzure corpus-run ──
用例      commission_happy_path（3 帧，录制结果 ok）
执行节点  ["CommissionStart", "commission_goto_reward", "commission_goto_commission",
           "commission_page", "commission_done"]
Pipeline  ok
断言      通过（与录制一致：ok）
```

这条闭环的意义：`--corpus-run` 与真机录制的语料**用同一套格式**，所以设备到手后
`record_golden.py` 录出来的目录可以**直接**丢给它跑，不需要改代码。

`--corpus-run` 目前断言的是「结束状态与录制一致」+ 打印执行节点序列；
逐帧决策比对（`*.decision.json`）等真机语料到位后再接——
合成帧的决策文件没有意义。

### OCR 模型

MaaFW 的 PP-OCR 模型不在 SDK 里，需要自己放。已从
[MaaCommonAssets](https://github.com/MaaXYZ/MaaCommonAssets/tree/main/OCR/ppocr_v4/zh_cn)
取 `ppocr_v4/zh_cn` 的 `det.onnx`(4.6MB) / `rec.onnx`(11MB) / `keys.txt` 放进
`resource/common/model/ocr/`。放好之后 MaaFW 日志里不再出现
`Failed to load det or rec` / `ocrer_ is null`，`CommissionPick` 里的 OCR 调用才能真的返回文本。

多语种（jp/tw/en）需要各自的模型；P1 再按需加，放 `resource/<server>/model/ocr/`。

## 断言层次

| 层 | 断言 | 启用时间 | 误报风险 |
|---|---|---|---|
| L1 | 最终状态一致 | 第一天 | 低 |
| L2 | 每帧选中的节点一致 | P1 | 低 |
| L3 | 点击落在同一 `area` 内 | P2 | 中（随机落点） |
| L4 | OCR 后处理结果一致 | P2 | 中（引擎差异） |
| L5 | 帧耗时在预算内 | P3 | 低（机器差异，放宽） |

L4 的坑：新旧 OCR 引擎不同，同一张图可能给不同结果。
对策：断言的是**我们的后处理**（`maazure_vision`），不是引擎输出。

## 反模式

| 反模式 | 后果 |
|---|---|
| 只在 CI 跑回放 | 开发时改坏了不知道 |
| 断言精确点击像素 | 随机落点 → 必然 flaky |
| JPEG 当回放帧 | 模板漂移 → 误判逻辑 bug |
| 只覆盖 happy path | 异常恢复无人验证 |
| corpus 进 git | clone 5 分钟 |

# 5.4 · Android 虚拟屏（画中画）截图

**位置**：`5-engineering` › 5.4 ｜ 前置：[5.1 构建](5.1-build.md)

> **为什么不用 ADB 截图**：ADB `screencap` 抓的是**整块屏幕**，通知、悬浮窗、其他 App、
> 状态栏全在里面；识别会被干扰，分辨率还随设备变。MaaEnd 的 APK 侧走的是另一条路。

## 1. 机制：特权进程 + 虚拟屏 + native controller

MaaEnd 的 Android 外壳是 [MaaFwApp](https://github.com/Aliothmoon/MaaFwApp)（子模块）。
它的 README 写得很清楚：

> MaaFramework 跑在 **Shizuku 或 root 拉起的特权进程**里，截屏和点击走**本机 native
> controller**，不经过 adb。
> **后台模式：在虚拟屏上跑任务**，手机可正常使用，分辨率可选 720P / 1080P。

拆开看是四件事：

| 组件 | 位置（MaaFwApp 源码） | 作用 |
|---|---|---|
| `VirtualDisplayManager` | `app/src/main/java/com/aliothmoon/maafw/remote/internal/` | 建一个 `VirtualDisplay`（`PUBLIC｜PRESENTATION｜OWN_CONTENT_ONLY｜SUPPORTS_TOUCH…`），把游戏搬进去 |
| 帧缓冲 | 同上（`monitorSurface`） | 虚拟屏的 `Surface` 就是截图源，等价于「只截游戏那块屏」 |
| native controller | `remote/MaaRunner.kt` | 直接给框架喂帧与触摸事件，不走 adb |
| `PipController` | `app/src/main/java/com/aliothmoon/maafw/ui/pip/` | 系统画中画，只是把虚拟屏画面缩成小窗**显示**，方便你看着它跑 |

虚拟屏默认参数（`constant/DefaultDisplayConfig.kt`）：

```kotlin
const val VD_NAME = "MaaFwVirtualDisplay"
const val WIDTH = 1280
const val HEIGHT = 720
const val DPI = 240
```

**1280×720 —— 和 MaaAzure 的固定分辨率完全一致**，资源不用重做。

`MaaRunner` 里还有一句关键约束：

> `screen_resolution` 必须与帧缓冲、触摸坐标空间三者一致，不一致时 screencap 立即失败。

## 2. 对 MaaAzure 意味着什么

好消息：

- 我们的 `pipeline` / `image` 是 1280×720 基准，**直接可用**；
- `interface.json` 里 `type: Adb` 的那一条会被外壳映射成它的 native controller，
  **不需要为 Android 另写一条**；
- 自定义识别走 PI 的 `agent` 字段：写一个 agent 进程注册 `CommissionPick` 即可。

限制（来自 MaaFwApp `INTEGRATION.md`）：

| 桌面端习惯 | 在 MaaFwApp 里 |
|---|---|
| GUI 放资源目录旁 | 构建期打进 APK，**换资源要重新出包** |
| `child_exec` / `child_args` 决定 agent 启动 | 不参与命令行，改由配方的 `agent.runtimes` 描述 |
| 改完资源刷新即可 | 要重装或清数据 |

所以要用这条路，**前提是能在这台设备上出一个带我们资源的 APK**。

## 3. 本机可行性（已实测）

| 依赖 | 现状 | 结论 |
|---|---|---|
| `aapt2` | `build-tools/35.0.1/aapt2` 是 **ARM aarch64** | 可在 chroot 里打 APK ✅ |
| JDK / Gradle | chroot 内 `/opt/jdk21-linux`、`/opt/gradle-9.8.0` | ✅ |
| Rust → Android | Termux 的 `clang 21.1.8` 原生 target 就是 `aarch64-unknown-linux-android24` | agent 可原生编译 ✅ |
| NDK | 只有 `linux-x86_64` 预编译（官方不发 arm64 宿主） | 用不到——Rust 侧用 Termux clang，不碰 NDK |
| MAA Android 运行时 | `MAA-android-aarch64` 发布包（60MB） | 需要下载 |

## 4. 要做的三件事（前提：必须出 APK）

1. **agent**：把 `CommissionPick` 从「进程内注册」改成 agent 进程（`MaaAgentServer`），
   用 Termux clang 编 `aarch64-linux-android`，产出 `jniLibs/libmaazure_agent.so`。
2. **配方**：写 `pi-profile.yaml`（`assets:` 指我们的项目根、`app.id`、
   `display.presets` 用 720P、`agent.runtimes` 指向 agent）。
3. **出包**：chroot 里 `./gradlew assembleRelease`，装到手机上，
   用**后台模式（虚拟屏 720P）**跑 委托任务。

做完这三步，「截屏干扰」这个问题从根上消失：抓的是虚拟屏，不是你的物理屏。

## 5. 与 ADB 路线的取舍

| | ADB 截图 | 虚拟屏（本条） |
|---|---|---|
| 画面干净 | ❌ 通知/悬浮窗/状态栏全在 | ✅ 只有游戏 |
| 分辨率固定 | ❌ 随设备 | ✅ 720P/1080P 可选 |
| 需要 root/Shizuku | ❌ | ✅ 必须 |
| 需要出 APK | ❌ | ✅ 换资源要重出包 |
| 后台可用 | 模拟器窗口挂后台 | ✅ 手机正常用 |

**结论**：真机验收必须走虚拟屏这条；ADB 只用来做「连得上设备」的冒烟。

## 6. 实测结论：Termux 进程里**加载不了** Android 版 MaaFramework

真机验证（Android 17 / SDK 37，`getconf PAGE_SIZE` = 4096，排除 16KB 页对齐问题）：

| 尝试 | 结果 |
|---|---|
| `dlopen(libMaaFramework.so)` 最小 C 程序 | **段错误**（库初始化阶段就崩） |
| 官方 `MaaPiCli --version`（同目录，`LD_LIBRARY_PATH` 已设） | **段错误** |
| 我们的 daemon 动态加载 | **段错误** |

也就是说这不是绑定层的问题，是 **MaaFramework 的 Android 构建要求 app 进程上下文**
（JNI/ART、linker namespace）。Termux 是普通 native 进程，装不下它。

**所以设备端只能走 MaaFwApp（APK）+ agent**；Termux 侧仍然可以做的两件事是：
截图（`screencap`）与输入（`input`），这两条已经验证可用。

### 已验证可用的部分：只读游戏浮窗

设备跑在 freeform 桌面模式时，游戏就是一个浮窗，实测数据：

```text
$ maazure-daemon --capture-window com.bilibili.azurlane --out frame.png
窗口物理矩形  left=45 top=90 1280x720
换算检查      1280x720 中心点 → 屏幕 (685, 450)
裁切后尺寸    1280x720
平均亮度      28.1/255
不同颜色      4096 (已封顶)
```

把游戏窗口的**逻辑**尺寸设成 `2844x1600`（桌面缩放 0.45）后，物理矩形正好是
`1280x720`——裁出来的帧与模板**同分辨率，零重采样**。这条链路是通的，
只是喂给谁的问题（框架得在 APK 里）。

```bash
# 复现：把游戏塞进 16:9 浮窗
TID=$(dumpsys activity activities | grep -o 'taskId=[0-9]*: com.bilibili.azurlane' | grep -o '[0-9]*')
am task resize $TID 100 200 2944 1800     # 逻辑坐标，×0.45 = 物理 45,90 1280x720
```

## 7. 实际走通的路：MaaFwApp APK（本机出包）

结论先说：**能在这台 arm64 手机上出包、装包、起 App**，全流程无需 x86_64 宿主。

### 7.1 绕过 NDK / CMake

官方 NDK 只发 `linux-x86_64` 宿主，SDK 自带的 `cmake 3.22.1` 也是 x86_64，
在这台设备上直接 `Syntax error`（是被 sh 当脚本解析了）。

但 MaaFwApp 的 native 模块只有 1,939 行 C/C++，而 **Termux 的 clang 原生 target
就是 `aarch64-linux-android34`**，于是直接手编：

```bash
./Android/build-native.sh <MaaFwApp 路径> <jniLibs 目录>
# → libbridge.so（帧缓冲/截图/输入注入）90K
# → liblauncher.so 13K、libagentexec.so 7.3K
```

编好后把 `externalNativeBuild` 从 `app/build.gradle.kts` 删掉，让 AGP 直接用 jniLibs。

### 7.2 三个「只有真机才踩得到」的构建坑

| 坑 | 现象 | 解法 |
|---|---|---|
| `aapt2` 从 Maven 下载的是 x86_64 | `AAPT2 Daemon startup failed` | `android.aapt2FromMavenOverride=<SDK>/build-tools/35.0.1/aapt2` |
| `aidl`/`zipalign` 同理 | `Error while executing .../36.0.0/aidl` | 把 35.0.1 的 ARM 版拷进 36.0.0 |
| 默认堆太小，R8 会挂 | 构建中途无声退出 | `org.gradle.jvmargs=-Xmx4g` |

### 7.3 产物异常：APK 里没有 AndroidManifest.xml

`assembleRelease` 报 `BUILD SUCCESSFUL`，但产物只有 dex/libs/assets，缺
`AndroidManifest.xml` 与 `resources.arsc`，`aapt2 dump badging` 直接说
「could not identify format of APK」。

中间产物是齐的：

```
app/build/intermediates/linked_resources_binary_format/release/processReleaseResources/
    linked-resources-binary-format-release.ap_   2.4MB / 969 个文件（含 manifest + arsc）
```

于是用它们把 APK 重组一遍（脚本见 `Android/fix-apk.sh`）：

```bash
unzip ap_ && unzip 残缺.apk     # 合并到同一目录
zip → zipalign → apksigner sign
```

重组后 `aapt2 dump badging` 正常：

```
package: name='com.aliothmoon.maafw.maazure' versionCode='1' versionName='7e2dc7d'
minSdkVersion:'28' compileSdkVersion='37'
```

**装包成功、App 正常启动**（`pm install` + `am start`，进程无崩溃）。

### 7.4 一条命令出包

```bash
./Android/build-apk.sh /sdcard/build_maaazure/stream.log
```

全部原始输出（gradle `--info` 级别）流式追加到日志文件；
`/sdcard/build_maaazure/` 下同时留签名好的 `MaaAzure.apk`。

## 8. 真机联调记录（含四个已修 bug 与一个未解限制）

### 8.1 已修

| # | 现象 | 根因 | 修法 |
|---|---|---|---|
| 1 | 根服务反复 `died unexpectedly` | 我们用 Termux sysroot 编 native，`NEEDED` 写成 `libEGL.so.1` / `libGLESv2.so.2`，app 里只有 `libEGL.so` | 头文件仍用 Termux（否则 `libunwind.a` 找不到），`-L` 指向 NDK `<api>` 库目录 |
| 2 | 特权进程起不来 | App 的 `startup_backend=SHIZUKU`，而设备上 root 一直可用 | datastore 里改成 `ROOT`（KernelSU allowlist 本来就有本包） |
| 3 | 游戏进程从没被拉起 | **我们的管线没有 `StartApp`** | 照 MaaEnd `OpenGame.json` 的写法，每个 `<Task>Start` 先经过 `<task>_start_game`（`action: StartApp` + `package`） |
| 4 | `StartApp` 之后必然 20s 超时 | 冷启动到主界面远超默认 20s | 加 `<task>_wait_loaded`（`timeout: 180000`） |

### 8.2 未解：虚拟屏拿到的是纯黑帧

```bash
$ dumpsys SurfaceFlinger --display-id
Display 11529215048162013319 (Virtual display): displayName="MaaFwVirtualDisplay"
$ dumpsys activity activities | grep 'Display #17' -A3
Display #17 ... com.bilibili.azurlane/com.manjuu.azurlane.MainActivity
$ screencap -d 11529215048162013319 -p vd.png
# 1280x720，亮度 0.0，非黑像素 0.0%，唯一颜色 (0,0,0) × 921600
```

结论与证据链：

1. 虚拟屏建出来了，游戏也确实被**移动到 Display #17**；
2. 但直接 `screencap -d` 那块屏也是**全黑**（不是我们截图实现的锅）；
3. 前台模式（`foreground: true`）下抓出来的帧同样全黑；
4. 对照组：同一时刻用我们自己的控制器抓**物理屏上的游戏窗口**，`1280x720`、平均亮度 28.1、
   4096 种颜色——游戏在物理屏渲染完全正常。

也就是说：**这个游戏（碧蓝航线，Unity）在这台设备上不会往虚拟屏/框架的合成目标里出画面。**
MaaFwApp 的 native controller 永远拿 VD 的 surface 当帧源，所以整条链路必然黑屏。

### 8.3 还剩的选项

| 选项 | 说明 |
|---|---|
| 换设备/换游戏验证 VD | 确认是游戏限制还是 ROM 限制（MaaEnd 在终末地上正常） |
| 让框架跑在物理屏 | MaaFwApp 的控制器恒为 VD，改不了；要么改外壳，要么自研 Android 壳 |
| 自研 Android 壳 | 用同一套 `VirtualDisplay` + surface 逻辑，但允许「抓物理屏 + 按窗口裁剪」；我们的 `--capture-window` 已经证明裁剪路径可用（1280×720 1:1） |

## 9. 一条硬规矩：不要改 `wm size` / `wm density`

排查时我为了拿到 1:1 的 1280×720 帧，用过 `wm size 1280x720`。这会把**整台手机**
的显示设置改掉（用户界面立刻变形），必须 `wm size reset` 才能还原。

| 命令 | 影响 |
|---|---|
| `wm size 1280x720` | 全局显示尺寸覆盖，用户立刻看到界面变小 |
| `wm density N` | 全局 DPI 覆盖 |
| `settings put global enable_freeform_support 1` | 可能影响桌面/分屏行为 |

**结论：设备侧任何全局显示设置都不要碰。** 需要 1:1 帧就走
`--capture-window`（裁窗口 + 缩放），它不改任何系统状态。

已还原（实测）：`wm size` 只剩 `Physical size: 1440x3200`，`wm density` 只剩
`Physical density: 600`，`enable_freeform_support` / `force_resizable_activities` 均为 0。

## 10. 白色主题：导航模板必须双份

真机 VD 出画面后，用「模板 × 真实帧」逐一比对，命中榜前 15 全是 `ui_white_*`：

```
0.997 ui_white_main_goto_fleet_white
0.996 ui_white_main_goto_guild_white
0.996 ui_white_main_goto_dormmenu_white
0.938 ui_white_main_goto_campaign_white      ← 主界面标志的白色版
```

而深色的 `ui_main_goto_campaign` **完全不匹配**——这个账号用的是游戏的
**白色主题**。所以 `global_home` 永远认不出主界面，委托流程必然失败。

修法：`xtask build-pipeline` 写出前，把 `ui/xxx.png` 的 `template` 扩成
`["ui/xxx.png", "ui_white/ui_white_xxx_white.png"]`（MaaFW 的 template 支持数组，
任一命中即命中）。命名规则有个坑：深色文件名本身就带 `ui_` 前缀，白色版是
`ui_white_<去掉 ui_ 的部分>_white.png`，直接拼会得到 `ui_white_ui_...` 找不到文件。

实测：13 个导航/页面节点变成双模板。

## 11. 真机点击有效性实测

在 VD 上用 `input -d <逻辑display> tap X Y` 逐个坐标点，量点击前后的帧差
（`screencap -d <SF display>` 取帧）：

| 坐标 | 帧差 | 说明 |
|---|---|---|
| (475,347) | **72.6** | `handler_login_check` 的 target 中心——确实有效 |
| (640,360) | 0.08 | 屏幕中心反而点不动（该处无响应区域） |
| (720,640) | 25.7 | 有响应 |

结论：
1. **点击注入是通的**，不是外壳的问题；
2. 我们资源里 `handler_login_check` 的 `target` 也是对的（点了画面确实变）；
3. 但点完游戏又回到同一屏，所以「识别 → 点击」会形成闭环，日志里表现为
   `commission_login_enter` 被反复执行（限速已加，防狂点）。

下一步要解决的是「点完为什么会回到标题屏」：可能是登录请求未完成、
或公告/更新弹窗在别的坐标上，需要再抓帧对比。

## 12. 事故与硬约束：不许乱点物理屏

联调时我写了个「扫点找可交互区域」的脚本，用 `input -d <逻辑display> tap` 逐点试探。
问题出在**逻辑 display id 取错**：我从 `dumpsys window displays` 里取了最后一个
`mDisplayId=`，那可能是物理屏（0）——于是点击全打到用户主屏幕上了。

### 现在的三道闸门

1. **显式 opt-in**：`tools/diag/scan_click.py` 与 `seek_main.sh` 没有
   `MAAGUI_ALLOW_INPUT=1` 一律拒绝执行；
2. **映射校验**：逻辑 display id 必须是从 SurfaceFlinger id 反查出来的虚拟屏，
   查不到就报错退出（绝不回落到 0）；
3. **只截虚拟屏**：所有抓帧都走 `screencap -d <SF id>`，不碰物理屏。

### 教训

- 「默认值」在会注入输入的脚本里是危险的：拿不到 id 就应该**失败**，不是回落；
- 探索型脚本必须先在小范围验证一次点击确实落在目标屏上，再放开扫描；
- 用户的主屏幕不是实验场——任何会注入输入的操作都应该先问一句。

# 5.1 · 构建与交叉编译

**位置**：`5-engineering` › 5.1 ｜ 前置：[2.1 分层](../2-architecture/2.1-layers.md) ｜ 后继：[5.2 测试](5.2-testing.md)

## 实测环境（不是假设）

| 项 | 值 | 状态 |
|---|---|---|
| 宿主机 | Termux aarch64（Android bionic） | Rust 1.98.1 能编译纯 Rust，**不能链接 glibc 的 MaaFW** |
| chroot | `~/.local/share/tmoe-linux/containers/chroot/debian-bookworm_arm64` | ✅ `cmake` `ninja` `pkg-config` `aarch64-linux-gnu-gcc` |
| 用户态模拟 | 容器内 `qemu-x86_64-static` 等全套 | ✅ 可跑 x64（慢） |
| NDK | `~/android-sdk/ndk/29.0.14206865` | ✅ 可构建 `aarch64-linux-android` |
| **缺** | `libclang`（bindgen）、`mingw-w64` | ❌ 需容器内 `apt install` |

结论：**开发在 chroot、发布在 CI、本机只做逻辑验证。**

## 目标矩阵

```
                        ┌─ aarch64-unknown-linux-gnu  本机开发 + 录像回放（有 MAA-linux-aarch64）
发布目标 ───────────────┼─ x86_64-unknown-linux-gnu   CI / Linux 用户
                        ├─ x86_64-pc-windows-msvc     ★ 主目标（用户是 Windows 模拟器）
                        └─ aarch64-linux-android     远期（框架跑在手机上）
```

## 本机（chroot）

```bash
cd tools/buildkit
cp env.example build.env        # 改 PROJECT_DIR / CHROOT_ROOT / RUST_TARGET
./10-enter.sh                   # 绑定挂载自检 + 容器内可见性检查
./20-bootstrap.sh               # 一次性：rustup + libclang + mingw + 交叉 target
./30-build.sh release
./40-verify.sh                  # 架构 / 动态依赖 / 新鲜度 / 冒烟
```

两个自检不能省（沿用 JMNeXt 的教训）：

1. **宿主机 → 容器可见性**：挂载掉了时报错是「目录不存在」，极易误判成项目被删；
2. **产物新鲜度**：构建失败时旧产物还在原地，`ls` 看到文件就以为成功。

## Windows 包的两条路

| 路径 | 可行性 | 做法 |
|---|---|---|
| **A. GH Actions `windows-latest`** | ✅ 推荐 | MSVC 原生，直接链 MaaFW 的 `.lib` |
| B. Linux 交叉 `x86_64-pc-windows-gnu` | ⚠️ 待验证 | 必须 `features = ["dynamic"]`，运行时加载 DLL |

原因：静态链接需要 MaaFW 的 **MSVC 导入库 `.lib`**，mingw 的 `ld` 读不了。
`dynamic` 让构建期不需要导入库，是 arm64 Linux 上出 Windows 包的**唯一现实路径**。

> **P0 待验证**：`maa-framework` 的 `dynamic` feature 是否真的让 build 阶段不依赖 `.lib`。
> 失败则 Windows 包一律走 Actions，本机只出 Linux 产物——不影响主线。

## 实测踩到的两个坑

1. **chroot 里必须挂 `/proc`**：不挂时 `rustup` 报 `Could not locate working directory: no /proc/self/exe`。
   ```bash
   su -c "mount -t proc proc $HOME/.local/share/tmoe-linux/containers/chroot/debian-bookworm_arm64/proc"
   ```
2. **SDK 路径**：`MAA_SDK_PATH` 指向解压目录（内含 `include/` `bin/`），
   运行时还要 `LD_LIBRARY_PATH=<sdk>/bin`，否则 `libMaaFramework.so` 找不到。

已验证：chroot 内 rustc 1.99.1 + `cargo build -p maazure-runner --features maa` 成功
（maa-framework 1.27.0 + MAA SDK 5.14.3 / linux-aarch64）。

## 容器内依赖（一次性）

```bash
apt-get install -y build-essential pkg-config libssl-dev \
    clang libclang-dev llvm unzip curl git ca-certificates \
    mingw-w64 gcc-x86-64-linux-gnu
curl --proto '=https' -sSf https://sh.rustup.rs | sh -s -- -y --profile minimal
rustup target add x86_64-unknown-linux-gnu x86_64-pc-windows-gnu aarch64-linux-android
```

`libclang` 是硬需求：`maa-framework` 用 bindgen 生成绑定，缺它会在几百行深的 build script 里报错。

## 增量编译

| 场景 | 耗时 | 说明 |
|---|---|---|
| chroot 原生 arm64 单 crate 增量 | 3–10s | 日常 |
| 全 workspace 首次 | 40–80s | 可接受 |
| 容器内交叉 x64 | 慢 2–3× | 只在出包时 |
| **Termux 侧 `cargo build`** | **必然失败** | 链接阶段找不到 `MaaFramework.so` |

所以：**在 Termux 只能 `cargo test` 地基与领域层**（没有 FFI 依赖），这正是分层带来的好处。

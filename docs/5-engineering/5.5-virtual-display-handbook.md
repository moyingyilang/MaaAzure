# 5.5 · 虚拟屏（VirtualDisplay）开发测试手册

**位置**：`5-engineering` › 5.5

> 这份文档与碧蓝航线无关，是**通用**的：任何「需要把某个 App 隔离到一块干净的屏幕、
> 抓帧不想要通知栏/悬浮窗干扰、并且能对它注入输入」的开发测试工具都用得上。
>
> 文中所有数字都来自本机实测（小米 24122RKC7C / Android 17 / SDK 37 / KernelSU root），
> 推断的部分会明确标 ⚠️。

---

## 0. 一句话结论

**用 `VirtualDisplay` 建一块独立屏幕把 App 搬进去，用 `screencap -d <SF display id>`
抓帧、用 `input -d <逻辑 display id> tap` 注入输入。** 抓到的就是那块屏的内容，
与用户主屏幕完全隔离。

代价：需要系统级权限建 VD（root / Shizuku / 系统签名），以及「抓 SF id、点逻辑 id」
这套 id 映射必须搞对，否则会出现「抓不到图」或**点到用户主屏幕上**。

---

## 1. 原理：三层结构

```
VirtualDisplay（逻辑显示器，有自己的 display id + Surface）
      │  应用把内容渲染进来（App 被移动到这块 display）
      ▼
Surface（帧缓冲）─────────────────► screencap -d <SF id>  取的就是它
      │
      ▼
SurfaceFlinger 合成到物理屏（可选：投到 PiP 小窗 / 不显示）
```

关键点：

- VD 是**真正的 display**（有 `displayId`、有 `DisplayDeviceInfo`），不是窗口；
- 它的 `Surface` 由你提供，App 渲染进去之后，你拿到的是**只有这个 App 的画面**；
- 这个 Surface **可以不投到任何物理区域**（用户看不到，后台跑），也可以投到画中画小窗给人看。

## 2. 建屏

### 2.1 系统 API

```java
VirtualDisplay vd = displayManager.createVirtualDisplay(
    "TestVD",                       // 名字，会出现在 displayName 里
    1280, 720, 240,                 // 宽、高、dpi
    surface,                        // 输出目标
    DisplayManager.VIRTUAL_DISPLAY_FLAG_PUBLIC
  | DisplayManager.VIRTUAL_DISPLAY_FLAG_PRESENTATION
  | DisplayManager.VIRTUAL_DISPLAY_FLAG_OWN_CONTENT_ONLY
  | DisplayManager.VIRTUAL_DISPLAY_FLAG_SUPPORTS_TOUCH);
```

| flag | 作用 | 缺了会怎样 |
|---|---|---|
| `PUBLIC` | 允许其他 App 被移动到这块屏 | 只有创建者自己的窗口能进 |
| `PRESENTATION` | 允许做展示型显示 | 部分 ROM 上无法承载普通 Activity |
| `OWN_CONTENT_ONLY` | 只承载自己的内容 | 用在「内容会被别人投进来」的场景时要小心 |
| `SUPPORTS_TOUCH` | 声明这块屏支持触摸 | **注入的触摸不生效** |

⚠️ 不同 ROM 对 flag 组合的容忍度不同，改组合后必须重新验证「画面有了 / 点得动」。

### 2.2 尺寸选择

- **固定 1280×720 + dpi 240** 是实践中最省事的一档：目标 App 大多按 16:9 布局，
  截图与模板/模型输入尺寸一致，零重采样；
- 需要更高清就用 1920×1080 + dpi 280；**不要**为了适配某个 App 去改全局 `wm size`（见 §8）；
- dpi 影响的是 **dp 尺寸**：同一个 1280×720 屏，dpi 240 → 853×480 dp；
  dpi 320 → 640×360 dp。App 的布局断点会因此变化，别随意改。

## 3. 三个 id、三个坐标空间（最容易翻车的地方）

### 3.1 两个 display id

| id | 从哪来 | 谁认它 |
|---|---|---|
| **SurfaceFlinger display id** | `dumpsys SurfaceFlinger --display-id` | `screencap -d` |
| **逻辑 display id** | `dumpsys display` / `dumpsys activity activities` | `input -d`、`am start --display` |

**两者不是同一个数**，混用会失败：

```
$ screencap -d 25 -p out.png            # 25 是逻辑 id
Error: Invalid display id 25            # screencap 只认 SF id

$ input -d 11529215049578793303 tap 10 10   # 这是 SF id
Error: Invalid arguments for display ID
```

### 3.2 实测输出格式

**① SurfaceFlinger 侧**

```
$ dumpsys SurfaceFlinger --display-id
Display 4630946338122044307 (HWC display 0): port=147 pnpId=QCM ... displayName=""
Display 11529215049578793303 (Virtual display): displayName="MaaFwVirtualDisplay"
```

- 物理屏：`(HWC display 0)`，id 是 **19 位**十进制；`displayName` 为空；
- 虚拟屏：`(Virtual display): displayName="<你建屏时给的名字>"` ← **靠这个名字认屏**。

**② 逻辑侧**

```
$ dumpsys display | grep -E "mViewports=|DisplayDeviceInfo\{"
mViewports=[DisplayViewport{type=INTERNAL, ..., displayId=0,
             uniqueId='local:4630946338122044307', ...}]
DisplayDeviceInfo{"内置屏幕": uniqueId="local:4630946338122044307", 1440 x 3200, ...}
```

映射规则：

| SF id | 逻辑 uniqueId 前缀 | 逻辑 id |
|---|---|---|
| 物理屏 `4630946338122044307` | `local:` | `0` |
| 虚拟屏 `11529215049578793303` | `virtual:` | 由系统分配（本机见过 17/19/23/25…） |

所以**推荐的映射方法**：

```bash
# 1) 按名字取 SF id
sf=$(dumpsys SurfaceFlinger --display-id | sed -n 's/.*Display \([0-9]*\) (Virtual display).*displayName="MaaFwVirtualDisplay".*/\1/p')

# 2) 在 dumpsys display 里找含这个 SF id 的 DisplayDeviceInfo 块，取其 displayId
#    该块里形如：DisplayDeviceInfo{... uniqueId="virtual:<pkg>,<name>,<sf>" ...} 
#    再往上找 mDisplayId=<N>/DisplayViewport{...displayId=N...}
logical=$(dumpsys display | awk -v sf="$sf" '
    $0 ~ sf { inblock=1 }
    inblock && /displayId=[0-9]+/ { match($0,/displayId=[0-9]+/); print substr($0,RSTART+10,RLENGTH-10); exit }
')
```

> ⚠️ **绝对不要**「取 `dumpsys window displays` 里最后一个 `mDisplayId=`」——那通常是物理屏 0。
> 这类「拿不到就回落 0」的默认值，是「点击打到用户主屏幕」事故的直接原因（§8）。

### 3.3 确认 App 在哪块屏

```bash
dumpsys activity activities | grep -E "^ *Display #|mResumedActivity|realActivity"
```

实测输出形如：

```
Display #25 (activities from top to bottom):
  * Task{... com.bilibili.azurlane/com.manjuu.azurlane.MainActivity}
```

### 3.4 坐标空间

| 空间 | 用在 | 注意 |
|---|---|---|
| VD 像素坐标 | `screencap -d` 出的图、`input -d` 的 tap 坐标 | 与 VD 的 width×height 一致 |
| 物理屏坐标 | 物理屏截图、`input tap`（不带 `-d`） | **不要**混用 |
| App 的 dp 坐标 | 布局、`uiautomator dump` | 需要按 dpi 换算 |

**三者必须一致**：如果 VD 是 1280×720，但你按 1440×3200 的坐标点，
点得动是运气，点不动是常态。

## 4. 抓帧

### 4.1 基本用法

```bash
screencap -d <SF display id> -p /sdcard/vd.png
# 输出 PNG；尺寸 = 该 display 的分辨率
```

要点：

- **必须用 SF id**（§3.1）；
- 不需要 root，但读另一个 App 的 VD 时通常需要 root/shell 权限；
- 抓帧耗时约 **100–300 ms**（1280×720，本机实测），不适合 60fps 级采集，
  做 UI 自动化（1–5 fps）够用；
- `screencap -d` 抓的是**合成后的最终帧**，所以用户看到的和你抓到的应当一致。

### 4.2 用亮度做「有没有画面」的硬验收

这是最省事的自动化断言：**黑屏 = 亮度 0、非黑像素 0%**。

```python
from PIL import Image
import numpy as np

def frame_stats(path):
    a = np.asarray(Image.open(path).convert("RGB"))
    return {
        "size": (a.shape[1], a.shape[0]),
        "brightness": float(a.mean()),                     # 0..255
        "non_black_pct": float((a.sum(axis=2) >= 30).mean() * 100),
        "unique_colors": len(np.unique(a.reshape(-1, 3), axis=0)),
    }
```

判读标准（实测标定）：

| 指标 | 黑屏 | 正常画面 |
|---|---|---|
| brightness | 0.0 | **160–200**（游戏/视频类） |
| non_black_pct | 0.0% | **> 90%** |
| unique_colors | 1 | 数千以上 |

> 单纯「亮度 > 0」不够：有些页面是深色背景，亮度可能只有 20–30。
> 建议同时要求 `unique_colors > 100`，避免把「纯色页」误判成有画面。

## 5. 注入输入

### 5.1 基本用法

```bash
input -d <逻辑 display id> tap X Y
input -d <逻辑 display id> swipe X1 Y1 X2 Y2 <duration_ms>
input -d <逻辑 display id> keyevent KEYCODE_BACK
```

要点：

- **必须用逻辑 id**；
- 坐标是 **VD 的像素坐标**；
- 需要 root 或 shell 身份（普通 App 无权往别的 display 注入）。

### 5.2 验证「点得动」

写自动化脚本前，先做一次**单点验证**：点一下，量点击前后的帧差。

```python
def diff(a, b):
    return float(np.abs(a.astype(np.float32) - b.astype(np.float32)).mean())
```

实测标定：帧差 **> 5** 说明画面确实变了；`< 1` 说明点在无响应区域。

## 6. 把 App 搬到 VD 上

### 6.1 官方路径（受限）

```bash
am start --display <逻辑 id> -n <pkg>/<activity>
```

实测在 **root / shell / system** 身份下都会被拒：

```
java.lang.SecurityException: ... launchDisplayId ...
```

这是 Android 的 display 权限模型限制（需要 `INTERNAL_SYSTEM_WINDOW` 级别的信任），
不是参数写错。

### 6.2 可行路径

| 路径 | 说明 | 代价 |
|---|---|---|
| **在 App 内部起 VD 并把任务跑在 VD 上** | 由 App 自己 `createVirtualDisplay` + 把自家内容/目标 App 移进去 | 需要改 App 或用支持此模式的壳（如 MaaFwApp） |
| 系统签名 / 平台密钥 | 拿到 `launchDisplayId` 权限 | 需要自签 ROM 或厂商配合 |
| Shizuku + 特定 API | 部分厂商 ROM 放开 | 机型相关，不可移植 |

⚠️ 结论：**「root 就能把任意 App 拉到 VD 上」是错的**。要么 App 自己配合，
要么改系统。

## 7. 黑帧排查清单（按命中率排序）

VD 建出来了、App 也在那块 display 上，但 `screencap -d` 拿到全黑——
按下面顺序查，前两条命中率最高：

| # | 症状 | 根因 | 处理 |
|---|---|---|---|
| 1 | VD 根本没建出来（`--display-id` 里没有 Virtual display 条目） | 配置里 `foreground: true` 之类的开关让外壳**不建 VD**，直接跑在物理屏 | 关掉前台模式，强制走 VD |
| 2 | VD 存在、App 也在上面，但全黑 | **App 把画面渲染到了物理屏**（很多 3D/Unity 游戏按物理 display 建 surface） | 抓物理屏 + 按窗口裁剪（绕开 VD） |
| 3 | 只有部分帧黑 | 目标 Surface 还没提交第一帧 | 建屏后等 1–2 s 再抓，或轮询到亮度 > 阈值 |
| 4 | 触摸无效 | 建 VD 时缺 `SUPPORTS_TOUCH` | 补 flag |
| 5 | 帧是黑的但 App 有声音/在动 | 抓的是**另一块同名的 VD**（旧 VD 没销毁） | 按 `displayName` + 建屏时间区分，先销毁旧的 |
| 6 | 进程直接段错误 | 在**非 App 进程**（如 Termux 普通 native 进程）里加载依赖 JNI/ART 的库 | 这类库只能跑在 App 进程里（本机实测：Termux 里 `dlopen(libMaaFramework.so)` 必崩，PAGE_SIZE 4096 已排除 16KB 页对齐问题） |

**第 2 条的实测证据**（本机，碧蓝航线 / Unity）：

```
物理屏窗口抓帧：1280x720，平均亮度 28.1，4096 种颜色   ← 正常
VD 抓帧（同一时刻）：1280x720，平均亮度 0.0，唯一颜色 (0,0,0) × 921600  ← 全黑
```

后来在同一台设备上，另一套外壳（同样 VD，但换了启动链与尺寸/flag）抓到了
**亮度 168.0、非黑 99.9%** 的正常帧。说明 VD 本身可用，**黑不黑取决于 App 是否
真的往你的 Surface 上渲染**——这是 App/ROM 行为，不是命令写错。

## 8. 安全红线（血的教训）

### 8.1 绝对不要改全局显示设置

| 命令 | 后果 |
|---|---|
| `wm size 1280x720` | 整台手机的显示尺寸被覆盖，用户界面立刻变形 |
| `wm density N` | 全局 DPI 覆盖 |
| `settings put global enable_freeform_support 1` | 改变桌面/分屏行为 |
| `overlay_display_devices` | 会额外建模拟 display，干扰 id 判定 |

想拿 1:1 的帧，正确做法是**抓物理屏 + 按窗口矩形裁剪**，而不是改系统分辨率。

### 8.2 注入输入的脚本必须带闸门

踩过的事故：脚本里用「取最后一个 `mDisplayId`」拿逻辑 id，结果拿到物理屏 0，
于是 `input -d 0 tap` 把点击全打到**用户主屏幕**上。

现在的三条硬规矩：

1. **显式 opt-in**：会注入输入的脚本，没有 `ALLOW_INPUT=1` 一律拒绝执行；
2. **映射校验**：逻辑 id 必须由 SF id 反查得到，**查不到就报错退出，绝不回落 0**；
3. **只截目标屏**：抓帧一律带 `-d <SF id>`，不碰物理屏。

### 8.3 探索型脚本要小步验证

「扫网格找可点位置」这类脚本，必须先做**单点验证 + 人工确认**，再放开批量——
它出错时的杀伤面是整块屏幕。

## 9. 通用工具骨架

### 9.1 shell

```bash
#!/system/bin/sh
# vd.sh —— 对指定虚拟屏抓帧 / 点击
set -u
NAME="${VD_NAME:-TestVD}"

sf_id() {
    dumpsys SurfaceFlinger --display-id \
      | sed -n "s/.*Display \([0-9]*\) (Virtual display).*displayName=\"$NAME\".*/\1/p" | head -1
}

logical_id() {
    sf=$(sf_id); [ -n "$sf" ] || { echo "找不到虚拟屏 $NAME" >&2; return 1; }
    dumpsys display | awk -v sf="$sf" '
        index($0, sf) { f=1 }
        f && match($0, /displayId=[0-9]+/) { print substr($0, RSTART+10, RLENGTH-10); exit }'
}

cmd="${1:-}"
case "$cmd" in
  capture)  sf=$(sf_id) || exit 1; screencap -d "$sf" -p "${2:-/sdcard/vd.png}" ;;
  tap)      lid=$(logical_id) || exit 1; input -d "$lid" tap "$2" "$3" ;;
  swipe)    lid=$(logical_id) || exit 1; input -d "$lid" swipe "$2" "$3" "$4" "$5" "${6:-300}" ;;
  info)     echo "sf=$(sf_id) logical=$(logical_id)" ;;
  *) echo "用法: vd.sh {capture [png]|tap X Y|swipe X1 Y1 X2 Y2 [ms]|info}"; exit 2 ;;
esac
```

### 9.2 断言模板（有画面）

```bash
vd.sh capture /sdcard/vd.png
python3 - <<'PY'
from PIL import Image; import numpy as np, sys
a = np.asarray(Image.open('/sdcard/vd.png').convert('RGB'))
bright = a.mean(); non_black = (a.sum(axis=2) >= 30).mean() * 100
colors = len(np.unique(a.reshape(-1, 3), axis=0))
ok = bright > 50 and colors > 100
print(f"亮度 {bright:.1f} 非黑 {non_black:.1f}% 颜色 {colors} → {'有画面' if ok else '黑屏/异常'}")
sys.exit(0 if ok else 1)
PY
```

## 11. 一页速查

```bash
# 有没有 VD、叫什么
dumpsys SurfaceFlinger --display-id | grep "Virtual display"

# VD 的 SF id（screencap 用）
dumpsys SurfaceFlinger --display-id | sed -n 's/.*Display \([0-9]*\) (Virtual display).*/\1/p'

# VD 的逻辑 id（input 用）—— 必须由 SF id 反查，别猜
dumpsys display | grep -E "DisplayViewport|DisplayDeviceInfo"

# 抓帧
screencap -d <SF id> -p vd.png

# 点击
input -d <逻辑 id> tap 640 360

# App 在哪块屏
dumpsys activity activities | grep -E "^ *Display #|realActivity"
```

**三条铁律**：
1. `screencap` 认 **SF id**，`input` 认**逻辑 id**，不能互换；
2. VD 抓到黑屏，先怀疑「App 没往这块 Surface 渲染」，再怀疑命令；
3. 不碰 `wm size` / `wm density`，不往不确定的 display 注入输入。

# 2.4 · FFI 边界

**位置**：`2-architecture` › 2.4 ｜ 前置：[2.1](2.1-layers.md) ｜ 后继：[3.1 Pipeline 规范](../3-authoring/3.1-pipeline-spec.md)

## 唯一入口

`crates/runtime/runner/src/ffi.rs` 是**整个仓库唯一**允许出现 `maa_framework::` 的文件。

```toml
# crates/runtime/runner/Cargo.toml（P0 引入）
[dependencies]
maa-framework = { version = "1", features = ["toolkit", "adb", "custom"] }
# Windows 发布版额外开 "win32"；交叉编译用 "dynamic"（见 5.1）
```

## 暴露给上层的窄接口

```rust
pub struct Engine { /* Controller + Resource + Tasker，不 pub */ }

impl Engine {
    pub fn connect(&mut self, cfg: &ControllerCfg) -> Result<()>;
    pub fn load_bundles(&mut self, paths: &[PathBuf]) -> Result<()>;
    pub fn run_pipeline(&mut self, entry: &str, overrides: &PipelineOverride) -> Result<TaskOutcome>;
    pub fn screenshot(&self) -> Result<Frame>;
    pub fn click(&mut self, p: Point) -> Result<()>;
    pub fn swipe(&mut self, from: Point, to: Point, ms: u64) -> Result<()>;
    pub fn stopping(&self) -> bool;
    pub fn post_stop(&self);
}
```

**不暴露**：`Context`、`Tasker`、`Job`、`Controller`、`Resource`。这些类型不出 `ffi.rs`。

## 为什么要这一层

| 问题 | 没有这层 | 有这层 |
|---|---|---|
| MaaFW 大版本升级 | 全仓 5 个 crate 受冲击 | 只改 `ffi.rs` |
| 想用录像回放测试 | 必须装 SDK + 模拟器 | `ReplayEngine` 实现同一 trait |
| `Context` 非 `Send` 的生命周期 | 渗到 5 个 crate，到处都是 `unsafe` | 关在一个文件里 |
| 换内核（假设） | 重写全仓 | 换一个实现 |

## Engine trait（给领域层看的抽象）

```rust
pub trait Engine {
    fn screenshot(&self) -> Result<Frame, EngineError>;
    fn click(&mut self, p: Point) -> Result<(), EngineError>;
    fn swipe(&mut self, from: Point, to: Point, ms: u64) -> Result<(), EngineError>;
}
```

两个实现：

```
Engine
├── MaaEngine      ffi.rs：真 Controller，P0
└── ReplayEngine   测试：读 golden corpus 的 PNG 序列，记录点击，P0
```

`ReplayEngine` 是 DEC-009 的载体：**领域逻辑必须在没有 MaaFW 的机器上可验证**。

## Custom 回调注册

```rust
// runner 启动时一次性注册
engine.on_custom_recognition("CampaignMapStep", |ctx, argv| {
    let view = battle::MapView::from_frame(argv.image)?;
    let cmd = machine.step(view)?;          // ← 纯逻辑，domain/battle
    match cmd {
        Some(Command::Click(p)) => ctx.post_click(p),
        _ => {}
    }
    Ok(true)
});
```

注意三点：

1. 回调里只做「观测 → 决策 → 投递」；**不做 IO、不等待**。
2. 从 `argv.image` 取图，**不要**自己 `post_screencap()`（多一次截图 = 多 350ms）。
3. 状态机实例存在 `Engine` 里（`HashMap<TaskId, Box<dyn Machine>>`），不要放全局静态。

## 已接通的调用（v1.27.0 + SDK 5.14.3，**编译通过**）

`crates/runtime/runner/src/ffi.rs` 里的实际映射，逐个都过了编译器：

| 我们的动作 | MaaFW Rust API |
|---|---|
| 初始化 | `Toolkit::init_option("./", "{}")` |
| 连设备 | `Controller::new_adb(adb_path, address, config_json, "")` |
| 连接 | `post_connection()` + `wait(id)` + `connected()` |
| 截图 | `post_screencap()` + `wait(id)` + `resolution()` |
| 点击 | `post_click(x, y)` + `wait(id)` |
| 滑动 | `post_swipe(x1, y1, x2, y2, duration_ms)` + `wait(id)` |
| 加载资源包 | `Resource::post_bundle(path)` → `job.wait()` == `MaaStatus::SUCCEEDED` |
| 注册自定义 | `register_custom_recognition` / `register_custom_action` |
| 绑定 | `Tasker::bind_resource` / `bind_controller` / `inited()` |
| 跑流程 | `Tasker::post_task(entry, override_json)` → `job.wait()` |

`resolution()` 返回 **i32**，我们的 `Frame` 用 u32，转换在 FFI 层完成（编译器抓到的第一个错就是这个）。

## 构建方式（实测）

```bash
# 1) 下 SDK
gh release download v5.14.3 --repo MaaXYZ/MaaFramework \
   --pattern "MAA-linux-aarch64-*.zip" --output MAA-linux-aarch64.zip
unzip -q MAA-linux-aarch64.zip -d MAA-linux-aarch64

# 2) 进 chroot（**必须挂 /proc**，否则 rustup 报 "no /proc/self/exe"）
su -c "mount -t proc proc $CHROOT/proc"

# 3) 编
MAA_SDK_PATH=$PWD/MAA-linux-aarch64 \
LD_LIBRARY_PATH=$PWD/MAA-linux-aarch64/bin \
cargo build -p maazure-runner --features maa
```

`maa` feature 默认关闭，所以没有 SDK 的机器（含 Termux 本体）仍然 `cargo test` 全绿。

## 尚未接通

| 项 | 现状 | 何时 |
|---|---|---|
| 截图**像素** | `Frame` 只有宽高；像素在 `MaaImageBuffer` 里，P2 做地图检测时补 `screenshot_rgba()` | P2 |

| 事件流 | `tasker.add_sink` 已可用，日志/看门狗在 P1 接 | P1 |

## 版本对齐

| 项 | 策略 |
|---|---|
| MaaFramework SDK | 固定版本，随发布包分发，**不依赖用户系统** |
| 升级触发条件 | 只有需要新节点的能力时 |
| 升级流程 | 改 `Cargo.lock` → 跑 golden corpus → 看 Protocol 变更表（v5.x 有版本表） |
| PI 协议版本 | `interface_version: 2` 固定；与 SDK 版本解耦 |
